BEFORE YOU START - WHAT SECRET_KEY ACTUALLY DOES HERE
------------------------------------------------------
It is worth knowing what you are protecting, so you can judge how
seriously to treat it.

In THIS project, SECRET_KEY is used to sign CSRF tokens
(CsrfViewMiddleware is enabled in settings.py). That is essentially
all of it:

  - Sessions are database-backed. There is no SESSION_ENGINE
    override, so the cookie only holds an opaque session ID and the
    data lives in Postgres. That means rotating SECRET_KEY later will
    NOT log your users out. This is not true of most Django apps, so
    it is worth knowing.
  - There is no password-reset flow, so no password-reset tokens are
    signed with it.
  - No other signing or encryption in the codebase uses it.

So the practical risk of the wrong SECRET_KEY is limited, but two real
things follow:

  a) Do not reuse your local development value. Your .env contains
     SECRET_KEY=django-insecure-change-this-later, which is published
     in this repository's history and is therefore known to anyone.
     A known key means anyone can forge CSRF tokens against your
     production site.
  b) Treat it as permanent. If you ever do need to change it, change
     it deliberately and expect currently-open forms to 403 once.

Why settings.py has no default for it, on purpose: a hardcoded
fallback would let the app boot with a key that is published in a
public repository. Failing loudly, as it does now, is the correct
behaviour. If you were tempted to "just add a default to make the
error go away", do not.


WHAT EACH VARIABLE IS FOR
-------------------------
Set all five. Each one causes a specific, confusing failure if wrong.

  SECRET_KEY
      Signs CSRF tokens. Missing -> the exact error you are seeing.
      A weak or published value -> forgeable CSRF protection.

  DEBUG
      Set to False. Turns off the debug traceback page and turns on
      SECURE_SSL_REDIRECT, SESSION_COOKIE_SECURE and
      CSRF_COOKIE_SECURE (all three are "not DEBUG" in settings.py).
      The value must be the exact string False. python-decouple
      parses it with strtobool, so False / 0 / no / off all work and
      anything else becomes True. A non-empty junk value silently
      leaves you in debug mode in production.
      Left unset it defaults to True, which is the wrong default for
      a public site.

  ALLOWED_HOSTS
      .onrender.com  (note the LEADING DOT)
      The leading dot is a wildcard, so it matches
      farmers-registry.onrender.com and any other subdomain. Without
      it Django rejects every request with DisallowedHost and the
      health check at / fails, which makes the deploy fail even
      though the build succeeded.
      If you add a custom domain later, add it here too.

  CSRF_TRUSTED_ORIGINS
      https://*.onrender.com
      Only needed because Render proxies over HTTPS and Django
      otherwise treats the request as cross-origin. Without it, every
      form POST (login, registration, farm registration) fails with
      "CSRF verification failed" while the pages themselves load
      fine, which makes it look like a login bug.

  DATABASE_URL
      The PostgreSQL connection string. Use the INTERNAL Database URL
      from the database's page, not the external one. Internal stays
      inside Render's private network, is not exposed to the internet
      and is faster. The external URL only resolves from outside.


OPTION A - Re-apply the Blueprint (recommended)
----------------------------------------------
Why this is the better option: render.yaml becomes the single source
of truth. Anyone (including future you) can rebuild the whole stack
from the repository, and the next deploy cannot drift from the file.
Option B leaves the settings living only in the Render dashboard,
where they are invisible in version control and easy to lose.

  1. Open the Render Dashboard.
  2. Go to: Blueprints  ->  New Blueprint Instance
  3. Connect/select the repository ZajarSaid/FARMERS_REGISTRY
  4. Click Apply.
  5. Confirm the values Render shows you before applying:
         Database        : farmers-registry-db
         Web service     : farmers-registry
         Python runtime  : 3.13   (read from .python-version)
         Build command   : bash ./build.sh
         Pre-deploy      : python manage.py migrate --noinput && ...
         Start command   : gunicorn Farmers_registry.wsgi:...
         Health check    : /
  6. Render generates SECRET_KEY for you (generateValue: true). You
     do not have to invent one, and you will not see its value, which
     is fine.
  7. If you already have a manually created web service or database
     with the same name, delete it FIRST, otherwise Apply creates a
     second set and you end up with two services and two databases.
     Two web services both answering to the same hostname is the
     usual cause of a "port is already in use" style failure.
  8. Apply triggers a deploy on its own, so you can go straight to
     STEP 4.


OPTION B - Set the variables by hand
-----------------------------------
Use this if you would rather not recreate the resources, for example
if the database already holds data you want to keep.

  1. Open the service -> Environment tab.
  2. Add these five variables:

     SECRET_KEY
       (generate one, do not type a value by hand)

     DEBUG             False
     ALLOWED_HOSTS     .onrender.com
     CSRF_TRUSTED_ORIGINS   https://*.onrender.com
     DATABASE_URL      (the internal connection string from the
                        farmers-registry-db database's page --
                        copy the "Internal Database URL", not the
                        external one)

  3. To generate a secret key, run this in your project folder:

       venv\Scripts\python.exe -c "from django.core.management.utils import get_random_secret_key as g; print(g())"

     It prints a 50-character random string. Paste that as the value.
     Do not reuse the value from your .env, and do not write the key
     into settings.py, render.yaml or any committed file.

  4. Save. Render restarts the service automatically.

  5. Option B does NOT read render.yaml, so you must also set the
     commands by hand. Open Settings -> Build & Deploy and confirm
     these match render.yaml exactly:

      Build Command    : bash ./build.sh
      Pre-deploy Cmd   : python manage.py migrate --noinput && python manage.py create_data
      Start Command    : gunicorn Farmers_registry.wsgi:application --bind 0.0.0.0:$PORT --workers 1 --access-logfile - --error-logfile -
      Health Check Path: /

  6. The Pre-deploy Command field is the one people miss. If you skip
     it, migrations never run, the tables do not exist, the health
     check at / hits the database and gets an error, and the deploy
     is reported as failed even though the build was perfect. If
     your dashboard has no Pre-deploy Command field at all, put the
     migrate command back at the front of the Start Command, which is
     the older arrangement that also works:

       python manage.py migrate --noinput && python manage.py create_data && gunicorn Farmers_registry.wsgi:application --bind 0.0.0.0:$PORT --workers 1 --access-logfile - --error-logfile -

  7. Note for later: with Option B, if you ever change render.yaml,
     nothing happens. Those values are not read again unless you
     re-apply the Blueprint or edit the dashboard by hand.

WHY THIS PUSH IS UNUSUALLY LARGE - AND WHY THAT IS OK
-------------------------------------------------------
You already removed venv/ from the working tree in commit 428f1a4.
The repository is still 56.76 MiB, and this push will be bigger than
your normal ones. That is expected, and here is why:

  Git stores every version of every file forever. Commit 428f1a4
  deletes venv/ from the current tree, but the ~10,080 files are still
  present in the history of earlier commits. The only way they leave
  the repository is by rewriting history (see the fallback below).

  This first push therefore has to transfer the whole repository to
  GitHub for the first time. Expect it to take noticeably longer than
  a normal push. A slow or seemingly stalled push during those minutes
  is normal. Let it run.

  Nothing about this affects the running application. Render builds
  from the tip of main, and the tip no longer contains venv/.

BEFORE YOU PUSH - CONFIRM WHAT IS GOING UP
-------------------------------------------
    git status
    git log --oneline -3

  Expect exactly this: two modified/added source files in commit
  428f1a4 plus the venv/ removal, and no uncommitted changes other
  than RENDER_DEPLOY_STEPS.txt if you have not committed it yet.

  Confirm venv/ really is untracked before you push:

    git ls-files venv | Measure-Object

  The number must be 0. If it is not, stop and do not push.

  Also confirm no secrets are being committed:

    git ls-files .env

  Must print nothing. .env holds your database password and must never
  be committed.


THE FALLBACK - PURGING venv/ FROM HISTORY
-----------------------------------------
ONLY do this if the plain push above fails or times out. Do not start
here.

    git filter-repo --path venv --invert-paths
    git push origin main --force

Understand the trade-off before running this:

  It is a HISTORY REWRITE, not a normal change. It creates entirely
  new commit objects for every commit in the repository, and
  git push --force then overwrites the published history on GitHub.

  Consequences to consider:
    - Anyone else who has cloned this repository, and any other
      branch, will get divergent history and will have to reclone
      from scratch. Their old local commits are not automatically
      saved.
    - If GitHub has open pull requests or branches pointing at the
      old commits, they can break or need to be recreated.
    - There is no undo at GitHub once the force push lands. Locally
      you would need a reflog recovery if you change your mind.
    - filter-repo may not be installed. Check with
      "git filter-repo --version" first; if it is missing you need
      "pip install git-filter-repo".

  Upside: the repository drops from roughly 57 MB to a few hundred KB,
  clones become fast, and 2.4 million deleted lines stop being part of
  your permanent history.

  Honest recommendation: try the plain push first and only reach for
  this if it genuinely fails. The large push is a one-time cost. The
  rewrite is permanent and affects other people.

------------------------------------------------
KNOWN WARNINGS - NOT BLOCKERS, BUT READ THESE
------------------------------------------------

1. FREE POSTGRES EXPIRES IN 30 DAYS
   Render deletes free Postgres databases 30 days after creation, with
   a 14 day grace period to upgrade. When that happens the site will
   fail with a database connection error and you will need to upgrade
   the plan. Note the date your database was created.

2. UPLOADED FILES ARE EPHEMERAL
   Farmer profile pictures and farm output CSVs are written to the
   container's local disk, which is wiped on every deploy and restart
   (free services cannot have a persistent disk). Files will disappear.
   The database rows survive; the image files do not.
   If that matters, you need either a paid plan with a persistent disk
   mounted at /opt/render/project/src/media, or a proper upload
   service such as S3 or Cloudinary.

3. Config_issues.txt CONTAINS A PLAINTEXT PASSWORD
   That file is committed to the repository, so the admin email,
   username and password are public to anyone who clones the repo.
   That password is a development credential and should be considered
   burned. Either delete the file from the repo or strip the password
   out of it, and use a different password in production. This is not
   something I changed, because removing it affects a file you may be
   relying on.

4. SECURE_HSTS_SECONDS IS NOT SET
   "manage.py check --deploy" reports this one warning. It is only a
   hardening recommendation. I left it off deliberately, because
   enabling HSTS carelessly is hard to undo in browsers. Set it only
   once the site is confirmed working over HTTPS.

5. ONE WORKER ONLY
   startCommand uses --workers 1, which is correct for a free Render
   instance (0.5 CPU, 512 MB RAM). Do not raise it or the service will
   be throttled or killed.
